## About the site

A static page with no framework and no build step. Every piece of content is
rendered from a single data file, so the markup never has to change when the
work does.

| File | Role |
|---|---|
| `index.html` | Page shell — structure only, no content |
| `data.js` | All content: systems, records, reporting surfaces, capability |
| `script.js` | Renders the page from `data.js`; draws the schematics |
| `style.css` | Design tokens, light and dark themes |

Deployed by GitHub Pages from `main`. Pushing is deploying.

## What's on it

- **Systems** — interactive module maps for two platforms, each with a
  canvas-drawn architecture schematic showing the real request and data path.
- **Records** — every project answered on the same six questions: context,
  constraint, architecture, rollout, outcome, and the trade-off I would
  revisit. Each carries an evidence tier stating what I owned outright and
  what I contributed to as part of a team.
- **Incident** — a production incident resolved mid-cycle with no downtime
  available, written up in six stages.
- **Reporting** — the reporting surfaces delivered and in build.
- **Capability** — technical areas with the confidence level I would defend
  in an interview, rather than a flat keyword list.

## A note on accuracy

The evidence tiers are deliberate. Work done inside an employer's product is
labelled as contributed, with my scope stated module by module; work I
conceived and built myself is labelled as owned. Employer work is described
generically by agreement — the class of system and my contribution to it,
without product or client specifics.

Where a project was a team effort, the record states which parts were mine
and which were not.
